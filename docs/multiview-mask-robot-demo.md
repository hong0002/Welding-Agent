# Multiview GPT conditioning and RB10 demo

Final GPT keeps RGB order `B/F/L/R/S1/S2/S3/S4/T`. Segment2's native defaults select cameras present in the query annotation (`mask.py`); the production sample artifacts contain F/R/S4. Only actual available binary masks among those cameras are used. Each selected mask is byte-copied into the attempt and overlaid onto its own RGB camera. `input_manifest.json` records camera order, image sizes, actual mask views and provenance. No missing mask is synthesized and no current mask is converted into a 3D path by the orchestrator.

`run_final_trajectory_prediction(mask_conditioning_views)` is a semantic Agent tool. Explicit F/R/S4 names in the human request bind its input selection; an unspecified/all-mask request uses all available views. Current manual/refined/unapproved and verified raw binary masks can condition a visualization prediction without F approval or a Trajectory3 prerequisite. The source scene hashes and sample/split binding are still checked. Multi-view predictions remain display-only, with `UNVALIDATED` status, no approval and no accepted F-only simulator proof. The old strict approved-F proof and Guided VLA transport are preserved separately.

In the web simulator tab, select the 3D result, then use **현재 경로 보기 → 로봇 시뮬레이션 보기 → 중지**. A renderable XYZ result with at least two points permits the robot action. `POST /api/simulator/robot-preview` accepts only job/artifact UUIDs, an optional stage index and an output-kind enum. Current-sample absolute sources prioritize the original STRICT sample-scene pipeline; it prepares native IK when needed without requiring a cached readiness flag. Display-only absolute GPT exports use the same pipeline without approval promotion. Relative/isolated sources select explicitly labelled DEMO. A failed strict launch is never retried as a demo. Launcher/assets/ownership errors remain truthful failures; stop the current window before switching modes. See [strict-robot-restore.md](strict-robot-restore.md) for the successful strict live check.

Demo packages are immutable, job-bound snapshots under `.cache/simulator/current-previews/packages/<UUID>`. `geometry.json` and `source-display.json` preserve original finite XYZ runs, coordinate frame and units. `demo_playback.npz` separately contains mapped Cartesian points, native IK joint angles, original point indices and independent run bounds; `demo_mapping.json` records uniform scale, anchor evidence and IK attempts. Native source/assets are read-only. The seed comes from an existing successful owned STP Robot Preview report and its hashed native solution, rather than a guessed TCP coordinate.

Mapping subtracts the first source point, uniformly fits the extent to 60 mm and translates to the successful RB10 TCP. The successful pose's orientation/tool convention is reused. If any point fails IK, there is exactly one smaller 12 mm attempt. At least two reachable, moving poses are required; omitted IK points are recorded. All surviving runs remain separate polylines. No extra joint-motion or synthetic trajectory is invented when a constant/degenerate source cannot produce movement.

The owned Isaac renderer loads RB10's actual URDF visual meshes and tool USD, animates six USD revolute-joint targets and corresponding kinematic link FK transforms, and draws red demo playback polylines. This is kinematic joint animation, not a physics simulation. Native source-frame XYZ is not claimed to be the robot's demo coordinates. The web viewport exposes owned-session live frames while available and latest captures afterward, clearing stale frames on stop. Outputs retain separate source and demo playback viewers.

Mandatory labels/flags: `ROBOT DEMO · VISUALIZATION ONLY`, `SOURCE TRAJECTORY TRANSFORMED`, `NOT ROBOT-EXECUTABLE`, `demo_transformed=true`, `source_preserved=true`, `robot_demo_only=true`, `physical_execution=false`, `physical_robot_executable=false`, `vla_orientation=false`, orientation from simulator policy. No physical endpoint is added.
